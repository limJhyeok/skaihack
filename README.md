# mockdrill — AI 실무 과제 모의고사 + 설명 리허설

2026 SK하이닉스 AI 해커톤 2차 예선 대비용 로컬 1인 연습 도구. 결정 기록은 `DECISIONS.md`.

## 실행

```bash
# 1) .env 작성 (앱 저장소 루트)
OPENAI_API_KEY=...
# OPENAI_BASE_URL=...            (선택)
MOCK_MODEL_STRONG=<출제·평가용 모델>   # 예: gpt-6.1-sol
MOCK_MODEL_FAST=<페르소나·판정용 모델> # 예: gpt-6-luna

# 2) 실행 (uv가 Python 3.12 가상환경과 의존성을 자동 준비)
./run.sh                 # http://127.0.0.1:8765
PORT=9000 ./run.sh       # 포트 변경
```

그 밖의 환경변수: `MOCK_WORKSPACE_ROOT`(기본 `~/mock-workspaces`, 앱 저장소와 겹치면 실행 거부), `MOCK_SEAL_KEY`(없으면 `~/.mockdrill/key` 자동 생성), `MOCK_DURATION_MIN`, `MOCK_REHEARSAL_COUNT`, `MOCK_REHEARSAL_SEC`, `MOCK_LANG`.

## 사용법

1. 홈 → **새 모의고사** → 도메인/과제 유형/난이도 선택(비우면 랜덤, 랜덤 도메인은 지난 세션 도메인을 피함) → **출제하기** (1~3분). 기존 세션은 홈의 세션 표에서 **열기**.
2. 완료 화면의 작업공간 경로를 복사해 그 경로에서 터미널을 열고 Codex/Claude Code로 작업.
3. 모드(실전/연습)를 고르고 **응시 시작** → 왼쪽에 README, 오른쪽 DM 패널에 현업 담당자와 Helper(플랫폼 안내).
   - Enter 전송, Shift+Enter 줄바꿈. 상단에 담당자 질문 수만 표시(공개된 사실 수는 숨김).
   - 응답 실패 시 메시지는 저장되고 **재전송** 버튼이 뜬다.
4. 상단 바: `02:59:46 남음` 타이머, 15·45·110·150·170분 단계 알림(토스트), 연습 모드에서만 **일시정지**. 시간이 끝나면 채팅이 막히고 제출 화면으로 이동.
5. **제출하고 리허설 시작** → 사용한 에이전트, 미커밋 변경이 있으면 자동 커밋 여부 → 제출. 실전처럼 실행 명령·포트는 입력하지 않고 제출 시점 작업공간 README에서 읽는다(못 찾으면 평가 때 실행 실패). 제출 화면에 지금 README에서 읽히는 값이 표시된다.
   - `git tag submission`, 스냅샷(`.git`·`node_modules`·`.venv`·`.env` 제외), 비밀키 검사, 과정 기록 수집.
   - Codex(`~/.codex/sessions`)·Claude Code(`~/.claude/projects`) 로그에서 작업공간 경로·응시 시간대가 맞는 세션의 프롬프트·토큰을 추출. 경로가 다르면 상단 **설정**에서 지정. 못 찾으면 "수집 안 됨"으로 진행(토큰은 제출 화면에서 직접 입력 가능).
6. 제출 완료 화면에서 **리허설 시작** (closed book: 서약 체크 / open book: 시간 제한 해제 가능) → 확인 문제가 한 문항씩, 문항당 5분, 붙여넣기 불가, 시간 초과 시 입력 내용 자동 제출 → 채점 결과(인지 관리 점수, 세부 항목 3개, 문항별 단계 판정·모범 답안·근거 좌표·다시 볼 곳). 미충족이 2문항 이상이면 **재심문** 1~2문항.
7. 리허설 결과 화면 → **평가 리포트 보기** (2~4분): 제출물 자동 실행(스냅샷을 임시 디렉터리에 풀어 실행 명령으로 기동, 최대 60초, `GET /` 확인, 로그 100줄, 테스트 자동 실행) + 기술·의도·인지 3축 + 소통 참고 점수, 문서-코드 불일치 표, 타임라인(테스트·확인 실행 줄 포함, 실패는 빨간 점), 다음에 바꿀 행동 3가지.
   - 의도 축 정량 지표에 에이전트가 **실제로 실행한** 테스트(횟수·통과/실패·실패 후 통과·마지막 통과 뒤 코드 커밋 수)·서버 확인(curl 등)과 커밋 크기 분포(최대 커밋 비중·마지막 30분 변경 비중)가 나온다. 실제 시험도 터미널 세션·git diff·테스트 실행 결과를 수집한다.
   - 자동 실행은 서버가 0.0.0.0에 바인딩됐는지도 확인한다(127.0.0.1에만 열리면 실전 브라우저 미리보기에서 열리지 않음).
   - README의 포트가 이미 사용 중이면 평가가 거부된다. 직접 띄워 둔 서버를 끄고 다시 평가.
   - Playwright가 설치되어 있으면 스크린샷도 저장(선택).
8. **숨은 요구사항 공개** → 사실표(발견 여부·발견 질문 번호), 놓친 사실마다 예시 질문·가장 가까웠던 내 질문·빗나간 이유·better_question, 점수와 발견률이 채워진 회고(`retro.md`) 편집·저장.

### 동작 추적 드릴

홈 → **동작 추적 드릴** (또는 `#drill`). 설계는 `docs/drill_design.md`.

1. **카드 만들기** (세션별, 2~5분): 제출 스냅샷과 그 세션 리허설의 오해 목록으로 카드 8장을 출제한다. 카드마다 상황을 주입해 코드를 실제로 실행하는 probe(pytest)를 함께 만들고, 스냅샷 임시 복사본에서 돌려 **관찰값을 정답으로 확정**한다. 예상과 다르거나 실패한 카드는 검수(관찰값 채택 / probe 수정 / 폐기)를 거친다. Python 스냅샷만 지원.
2. **드릴 시작**: 코드 닫고(카드당 90초) 또는 코드 보고(180초, 근거 파일 전체를 강조 없이 표시). 안 푼 카드 → 마지막에 틀린 카드 순으로 나온다.
3. 카드는 **기능 흐름**(사용자 행동 → 결과, 용어 풀이 1~2문장) + **상황** + 칸 2~3개. 기준·테스트 번호(B1, T8 등)나 함수명은 문장에 쓰지 않는다(출제 시 검사, 위반하면 재출제). 칸을 고르거나 값을 입력 → 즉시 채점(정확 일치, LLM 호출 없음) → 실행 결과, 동작 이유, 근거 코드(강조), probe 코드. 정답이 이상하면 **정답이 이상함**으로 신고하면 통계와 다음 드릴에서 빠진다.
4. 요약: 카드·칸 정답률, 평균 시간, 틀린 카드의 결함 패턴.

**새 문제**: 드릴 화면의 **새 문제 만들기**(4~8분) → 처음 보는 작은 업무 시스템 저장소(FastAPI, 파일 10개·코드 700줄 이하)를 `MOCK_WORKSPACE_ROOT/drills/<repo_id>/`에 만들고 결함 2~3개와 미끼 1개를 심는다. 결함은 최근 30일 드릴에서 틀린 패턴일수록 자주 고르고, 정원·동시 수정·날짜 경계 중 하나는 반드시 넣는다. 저장소 테스트가 통과해야(결함은 테스트에 걸리지 않게 숨김) 카드를 출제한다. 저장소를 에디터로 15분 읽은 뒤 코드 닫고 모드로 푼다. 결함 사양은 저장소가 아니라 `data/drills/repos/<repo_id>/repo.json`에만 있다.

probe는 `OPENAI_API_KEY`를 가짜 값, `OPENAI_BASE_URL`을 닫힌 포트로 바꿔 실행한다. 저장: `data/drills/decks/<deck_id>/deck.json`, `data/drills/runs/<run_id>/run.json`.

### 성공 기준 드릴

홈 → **성공 기준 드릴** (또는 `#criteria`). 설계는 `docs/flow_drills_design.md` 3·4절(B).

1. **새 정책 묶음 만들기** (2~5분): 업무 명세 문서(6,000~9,000자, 정책이 본문·표 비고·단서 조항·부록에 흩어짐), 원자 단위 정책 8~12개, 정책을 지키는 순수 Python 정답 구현(함수 3~5개), 정책을 하나씩 어긴 결함 버전 5~7개를 한 번에 출제한다. 정책 예시를 정답 구현에 **실제로 실행해** 기대값과 같은지, 결함 버전마다 자기 정책 예시로 잡히는지 확인하고, 실패하면 사유를 피드백해 최대 3회 다시 출제한다. 설계 개념 카드(업무 기준일, 정원+대기 승격 등) 2~3개를 심고, 결함은 카드의 순진한 실패에서 나온다.
2. **시작** (기본 20분): 왼쪽에 명세 문서, 오른쪽에 함수 모양(이름·입력·출력). 함수마다 입력을 채우고 기대 출력을 적어 예시를 추가한다. 예시는 바로 저장되어 나갔다 와도 이어서 쓴다. 시간이 끝나면 자동 제출.
3. **채점** (LLM 없음): 정책 이해 정확도(내 기대값 = 정답 구현 출력인 비율), 결함 검출률(맞는 예시로 잡은 결함 버전 비율). 틀린 예시의 기대값이 어떤 결함 버전의 출력과 같으면 그 결함이 어긴 정책을 오해한 것으로 진단한다. 놓친 결함마다 정책·문서 위치·원문과, 그 결함을 잡는 모범 예시를 보여 준다.

저장: `data/drills/bundles/<bundle_id>/bundle.json`, `data/drills/sheets/<sheet_id>/sheet.json`. 정답 구현·결함 버전은 앱 밖 하위 프로세스(`python -I`, 허용 import만, 케이스당 2초)에서 실행한다.

### 읽기·정리 드릴

홈 → **읽기·정리 드릴** (또는 `#reading`). 설계는 `docs/flow_drills_design.md` 4.2절(A). 성공 기준 드릴과 같은 정책 묶음을 쓴다.

1. 묶음을 고르고 **시작** (기본 25분): 왼쪽 명세 문서를 읽으며 오른쪽 칸에 요구사항을 한 줄에 하나씩 적는다. `#` 줄은 묶음 제목. 입력할 때마다 저장되고, 시간이 끝나면 자동 제출. 타이머 옆 **일시정지**로 시계를 멈출 수 있다(문서·답안은 계속 보이고 쓸 수 있음). **나가기**하면 자동으로 멈춘다. 멈춘 시간은 소요 시간에서 빠지고, 결과에 일시정지 횟수가 표시된다.
2. **채점** (LLM 1회): 숨은 정책 목록과 대조해 정책마다 반영 / 부분 반영 / 잘못 해석 / 누락, 내 항목마다 정책 해당 / 문서에 있음(감점 없음) / 문서에 근거 없음 / 문서와 어긋남. 정책 포착률 = (반영 + 부분 × 0.5) / 정책 수.
3. 결과: 놓친 정책마다 문서 위치·원문, 내가 쓴 항목과의 차이, 그 정책을 놓친 구현에서 생기는 일. **같은 문서 다시 풀기**로 같은 제한 시간의 새 답안을 시작한다(목록에서는 푼 묶음의 버튼이 **다시 풀기**). 지난 답안은 목록에 남는다.

다른 드릴(성공 기준·AI 변경 검토·변경 대응)을 한 묶음은 정책 목록을 이미 본 것이라 "이미 봄"으로 표시된다. 같은 묶음이면 읽기·정리 → 성공 기준 순서로 푼다. 저장: `data/drills/reads/<read_id>/read.json`.

### AI 변경 검토 드릴

홈 → **AI 변경 검토 드릴** (또는 `#review`). 설계는 `docs/flow_drills_design.md` 4.3절(C). 같은 정책 묶음을 쓴다 (LLM 호출 없음).

1. 묶음을 고르고 **시작**: 카드 3~5장. 카드마다 "에이전트가 방금 작성한 코드"(정답 구현 또는 결함 버전의 함수 하나, 그 함수가 읽는 기준표 포함)와 관련 요구사항(그 함수에 결과가 달린 정책)을 보여 준다. 한 묶음에서 같은 함수는 한 번만 나오고, 다시 풀면 덜 본 결함부터 나온다.
2. 위반 없음 / 위반 있음을 고르고, 위반이면 어긴 요구사항과 줄(클릭)을 고른다. 장당 2~3분 목표 (시계는 위로 셈, 자동 제출 없음).
3. 즉시 채점: 위반 여부, 요구사항(결함의 정책 또는 이 결함 버전에서 실제로 예시가 틀리는 정책이면 정답), 줄(결함 치환으로 바뀐 줄). 결과에 업무에서 생기는 일, 정책 원문, 예시 실행 결과(요구사항대로 vs 이 코드), 바뀐 줄 표시, 정답 코드 비교.

저장: `data/drills/reviews/<review_id>/review.json`.

### 변경 대응 드릴

홈 → **변경 대응 드릴** (또는 `#change`). 설계는 `docs/flow_drills_design.md` 4.4절(D). 같은 정책 묶음을 쓴다.

1. 묶음을 고르고 **시작**: 처음 시작할 때 묶음의 정책 변경 공지 3~4개를 출제한다 (LLM 1회, 보통 1~3분, 실패하면 최대 3회). 변경마다 정답 구현에 대한 치환을 받아 **모든 정책 예시를 실행해** 영향 범위를 정한다.
2. 카드마다 현업 공지를 읽고 ① 고칠 요구사항 ② 기대값이 바뀌는 성공 기준 예시와 새 기대값 ③ 고칠 코드 위치(함수·기준표)를 고른다. 장당 3~5분 목표.
3. 즉시 채점 (LLM 없음): 요구사항·예시·코드 위치마다 맞춤 / 놓침 / 불필요, 새 기대값 정확도. 정답 = 값이 바뀐 예시, 그 예시의 정책(문구가 그대로인 파급 정책 포함)과 출제자가 문구를 바꾼 정책, 치환이 들어간 정의. 바뀐 기준표를 읽기만 하는 함수는 골라도 감점하지 않는다.

저장: 변경은 `bundle.json`의 `changes`, 풀이는 `data/drills/responses/<response_id>/response.json`.

## 데이터 위치

- `data/sessions/<session_id>/` — `session.json`, `problem_public.json`, `sealed.bin`(숨은 정보, Fernet 암호화), `chat.jsonl`(담당자 대화 + 턴별 공개 판정), `helper_chat.jsonl`, `events.jsonl`(start/pause/resume/alert/submit), `snapshot.tar.gz`, `submission.json`(제출 결과·비밀키 검사), `process.json`(커밋·문서·에이전트 로그 요약), `agent_logs/`(원본 로그 사본), `snapshot/`(리허설·평가용으로 푼 스냅샷), `rehearsal.json`, `run.log`·`run_result.json`(자동 실행), `report.json`, `reveal.json`, `retro.md`
- `data/rehearsals/<id>/rehearsal.json` — 단독 리허설
- `data/settings.json` — 에이전트 로그 경로 수동 지정값
- `data/usage.jsonl` — 모든 LLM 호출의 토큰 사용량
- `~/mock-workspaces/<session_id>/` — 사용자 작업공간 (README, data/, .env.example, .gitignore, 초기 커밋)
