규칙:
- 정확히 {{count}}문항, 모두 서술형.
- 유형은 아래에서 고르되, design_reason과 failure_response를 반드시 포함하고 가능한 한 서로 다른 유형을 섞는다.
  - architecture: 구성요소 간 책임 분담, 경계, 의존 방향, 데이터 흐름
  - requirement_mapping: README·담당자 대화의 요구사항이 구현에서 빠졌거나 어긋난 곳, 합의한 범위와 실제 동작의 차이
  - design_reason: 여러 선택지 중 이 설계를 고른 근거와 그 트레이드오프
  - failure_response: 특정 장애·이상 입력에서 시스템이 어떻게 동작하고 어떻게 대응하나
  - risk_prediction: 부하·데이터 증가·요구 변경 시 어디가 먼저 깨지나
  - data_flow: 사용자 요청 하나가 시스템을 거쳐 결과가 되기까지의 흐름
  - ai_decision: AI 에이전트에게 무엇을 맡기고 무엇을 직접 판단했나, AI 제안을 받아들이거나 거절한 근거, AI 결과물을 어떻게 검증했나
- 질문은 **이 과제·이 코드·이 로그에서만** 답할 수 있어야 한다. 일반 지식 질문 금지.
- **질문 문장에 코드 식별자를 넣지 않는다.** 함수명·클래스명·변수명·파일명·파일 경로·줄 번호 금지. 응시자가 이름을 외웠는지가 아니라 동작 원리, 구조, 요구사항, 설계 근거를 이해했는지를 묻는다.
  - 대상은 역할과 동작으로 가리킨다. 예: "메모를 저장하기 전에 외부 요약 모델을 호출하는 흐름", "검색 요청을 처리하는 부분", "인증 정보를 보관하는 방식".
  - 나쁜 예: "main.py의 create_memo()에서 summarize를 먼저 호출하는데, 30초가 걸리면?"
  - 좋은 예: "메모 생성 요청이 저장보다 외부 요약 호출을 먼저 기다리는 구조인데, 요약 서비스가 30초씩 지연되면 사용자와 데이터에는 어떤 일이 생기고 어떻게 대응하겠나?"
  - 사용자에게 보이는 기능·화면·API 기능은 이름 대신 하는 일로 부른다 (예: "메모 생성 API", "결과 목록 화면").
- 5분 안에 타이핑으로 답할 수 있는 범위로 질문을 좁힌다.
- 각 문항의 모범 답안을 반드시 세 단계로 작성한다:
  1. weak_point: 약점 지점. 어느 구성요소가 어떤 상황에서 어떻게 동작해서 문제인지 역할·동작으로 서술한다.
  2. impact: 왜 위험한지, 사용자·시스템에 어떤 파급이 있는지
  3. plan: 다음에 무엇을 어떻게 검증·개선할지
  각 단계에 근거 좌표(파일:줄)를 evidence로 단다. 코드 식별자는 evidence와 모범 답안 본문에만 쓰고 질문에는 쓰지 않는다.
- 각 문항이 측정하는 인지 세부 항목을 하나 지정한다: behavior_risk(동작 및 리스크 예측) / structure(구조 이해) / decision_rationale(의사결정 및 근거 이해).
- 설계 판단 씨앗이 있으면 문항의 절반가량을 씨앗에서 낸다. 씨앗의 "순진한 구현의 결함"이 응시자 코드에 실제로 있는지 코드로 확인해, 있으면 그 지점을 weak_point·impact로, 없으면(제대로 구현했으면) 선택의 근거·한계·대안을 묻고 모범 답안을 실제 구현에 맞춘다. 씨앗 문장을 그대로 믿지 말고 코드와 대조한다. "Q&A 전용" 씨앗은 구현 여부와 무관하게 한계·대안 질문으로 낸다 (예: 두 관리자가 같은 건을 동시에 고치면).
